# Design: se-foundations curriculum

Public learning repo for one specific learner, shareable with anyone in the
same position. Written entirely in Markdown plus small Python, SQL, and CSV
files. No web app, no build step.

## Learner profile

- Recent UNC grad, information science + biology. Starting a one-year MS in
  information science now. Summer as a customer success intern at SAS.
- Comfortable talking to customers and explaining things. Not a programmer.
  Has never written SQL or called an API. Knows Excel.
- Goal: entry-level solutions engineer, implementation specialist, or
  solutions consultant at a B2B SaaS company, applying now for roles in NYC.
- Every listing asks for SQL. Needs résumé-visible proof in 4 to 8 weeks,
  not a semester.
- Confidence is a real constraint. She believes she "lacks the knowledge
  base." The repo has to keep proving to her that she now knows things.

## Tone and writing rules for every module

- Second person, direct, warm but not cheerleading. No "Great job!" No
  exclamation marks in headings.
- Assume zero prior knowledge of the topic but full adult intelligence.
  Never say "simply" or "just." Define every term the first time it appears
  and add it to `glossary.md`.
- Every concept is tied back to a moment in the SE job: a customer question,
  a demo, a discovery call, an integration that broke. That is the thread that
  makes the modules compound.
- Short paragraphs. Code in fenced blocks with language tags. Tables for
  comparisons. No walls of text.
- Every module ends with three things she can now say out loud in an
  interview, phrased as first-person sentences.
- Worked examples first, then exercises. Solutions in a separate file so she
  tries first.

## Fixed module template

Every `modules/NN-slug/README.md` has exactly these sections in this order:

1. `# NN. Title`
2. `## Why an SE needs this` (3 to 6 sentences, one concrete job scenario)
3. `## What you will be able to do` (bullet list, observable outcomes)
4. `## Concepts` (the teaching, with worked examples)
5. `## Walkthrough` (a hands-on guided task on the repo dataset or a public
   resource, every command shown, expected output shown)
6. `## Exercises` (5 to 10, easy to hard, numbered; answers in
   `solutions.md` in the same folder)
7. `## Checkpoint` (a 5-question self-quiz with answers folded under a
   `<details>` block, plus "You can now say:" with three interview sentences)
8. `## Put it on your résumé` (one or two bullet lines she can literally
   paste once she finishes, with the metric or artifact filled in)
9. `## Go deeper` (3 to 5 free resources, each with one line on why)

Module folders also contain any exercise files (`.sql`, `.py`) and
`solutions.md`.

## Dataset: "Northwind Analytics" fictional B2B SaaS

Generic SaaS, not healthcare, because the target job is SaaS. One dataset
used from module 03 through 09 so that queries in later modules build on
tables she already knows. Generated by `datasets/generate.py`, seeded, stdlib
only (`random`, `csv`, `datetime`), so it runs on any Python 3 with no
installs. Roughly:

| table | rows | columns |
|---|---|---|
| plans | 4 | plan_id, name (Free, Starter, Pro, Enterprise), monthly_price, seat_limit |
| customers | 200 | customer_id, company_name, industry, country, region, signup_date, csm_owner |
| subscriptions | ~260 | subscription_id, customer_id, plan_id, start_date, end_date (nullable), status (active, churned, trial), seats, mrr |
| users | ~2,000 | user_id, customer_id, email, role (admin, member, viewer), created_at, last_login_at |
| usage_events | ~40,000 | event_id, user_id, customer_id, event_type (login, report_created, export, api_call, dashboard_viewed), event_ts |
| support_tickets | ~1,500 | ticket_id, customer_id, opened_at, closed_at (nullable), priority, category, satisfaction_score (nullable 1-5) |
| invoices | ~2,500 | invoice_id, subscription_id, invoice_date, amount, status (paid, overdue, void) |

Deliberate realism baked in: some customers churn, some have multiple
subscriptions over time (upgrades), some tickets are unresolved, some
invoices overdue, nulls exist, a few duplicate-looking company names with
different ids, dates spanning 2024-01-01 to 2026-08-31. The modules point at
these quirks as teaching moments.

SQL engine: DuckDB, because it reads CSVs directly with no server and
installs with one `pip install duckdb`. Module 03 shows the DuckDB CLI and
the Python one-liner. Mention that the same SQL runs on Postgres and
Snowflake with minor differences, and note the differences when they matter.

## Module content specs

### 00-start-here
How to use the repo. The 8-week schedule (weeks 1-2 modules 00-03, week 3
module 04, week 4 module 05 and 09 part 1, weeks 5-6 modules 06-08, week 7
module 09 finish, week 8 modules 10-11). 90 minutes a day. How to take notes
that turn into résumé bullets and LinkedIn posts (the "learning log" habit:
what I built, what broke, what I understood). Setup: install Python 3,
DuckDB, VS Code, Git, Postman, a GitHub account. Verify commands. A short
section on imposter syndrome that is practical, not therapeutic: the SE role
is judged on explaining and connecting, which she already does; the technical
floor is finite and this repo is the floor.

### 01-how-software-works
Client and server. What a web request is. Front end vs back end vs database.
What "the cloud" is. What an API is at concept level (detail in 06). What a
database is and why companies have many. SaaS vs on-prem. Multi-tenant. The
lifecycle of one button click in a SaaS app, traced end to end. Draw it.
Walkthrough: open browser dev tools on any site, watch the network tab, find
a JSON response. Tie-in: how to answer "how does your product store our
data" on a customer call.

### 02-terminal-and-git
Terminal navigation on Windows (PowerShell and Git Bash) and Mac. cd, ls,
mkdir, cat, running python and duckdb. Git: init, add, commit, push, clone,
branch, .gitignore, what a README is. Create her own GitHub repo for her
learning log. Tie-in: SEs live in the terminal during POCs and every SE
team keeps demo assets in Git.

### 03-sql-foundations
SELECT, FROM, WHERE, ORDER BY, LIMIT, DISTINCT, comparison and logical
operators, NULL handling, aggregate functions, GROUP BY, HAVING, aliases,
basic date functions. Each concept: plain-English question, the query, the
result. 10 exercises on the dataset ranging from "list all Enterprise
customers" to "monthly ticket volume by priority in 2026." Tie-in: the
discovery-call moment when a customer asks "can you show me which of our
accounts are inactive."

### 04-sql-intermediate
INNER, LEFT, RIGHT, FULL joins with a diagram and the row-count intuition.
Self joins. Subqueries in WHERE and FROM. CTEs. CASE. Window functions:
ROW_NUMBER, RANK, LAG, running totals, partition by. Common interview
patterns: second-highest, dedupe, gaps and islands lite, cohort by signup
month, churn rate. 10 exercises. A "SQL interview question bank" section
with 15 questions in the style of DataLemur, with solutions. Tie-in:
building the one query that makes a demo dashboard.

### 05-data-modeling
Primary and foreign keys. One-to-many, many-to-many, junction tables.
Normalization in plain terms (why not one giant spreadsheet). Reading an
ERD. Star schema basics: facts and dimensions. Walkthrough: draw the ERD of
the repo dataset in Mermaid, then design the schema for a new feature
("customers can tag tickets"). Tie-in: the implementation-kickoff moment when
a customer sends their schema and asks how it maps to yours. Data mapping
exercise: map a fictional customer's CSV export to the dataset tables.

### 06-apis-and-http
HTTP methods, URLs, query params, headers, request and response bodies,
status codes (200, 201, 400, 401, 403, 404, 429, 500) and what each means on
a support call. JSON structure. Authentication: API key, bearer token, OAuth
2 at concept level. Rate limits. Pagination. Reading API documentation: a
guided read of one real public API's docs. Postman: collections,
environments, variables. Walkthrough with a free, no-key public API (for
example the Open-Meteo weather API or the GitHub REST API unauthenticated
endpoints). Then a walkthrough of a key-based API (e.g. NASA APOD with the
DEMO_KEY). Tie-in: the "does your product have an API" question and the
"integration is failing with a 401" support escalation.

### 07-python-for-ses
Enough Python to be dangerous: variables, lists, dicts, loops, functions,
f-strings, reading and writing files, `requests`, `json`, error handling
with try/except, running a script from the terminal. Explicitly not:
classes, algorithms, LeetCode. Walkthrough: script that calls a public API,
parses JSON, writes a CSV, then loads it into DuckDB and runs a query.
Second walkthrough: read `usage_events.csv`, compute something with plain
Python, then do the same in one SQL query to show why SQL wins for tabular
work. Tie-in: the POC where the customer's data arrives as a weird JSON
export and someone has to turn it into tables.

### 08-integrations-and-architecture
How systems connect: batch file transfer (SFTP, CSV), REST API sync,
webhooks (push vs pull, with a diagram), ETL and ELT, iPaaS tools (Zapier,
Workato, MuleSoft at concept level). Identity: SSO, SAML vs OIDC, SCIM, at
the level of answering a security questionnaire. Cloud basics: regions,
compute, storage, managed databases, the three big providers, what "we are
hosted on AWS in us-east-1" means. Data warehouse vs database. Security
vocabulary: encryption at rest and in transit, RBAC, SOC 2, GDPR, data
residency. Walkthrough: draw an architecture diagram in Mermaid for
"customer's CRM syncs to our product nightly and sends webhooks on ticket
creation." Exercise: answer 10 sample security-questionnaire questions in
plain language. Tie-in: the solution-design deliverable an SE produces after
discovery.

### 09-capstone-pipeline
The résumé project. Build end to end: pick a public API, pull data with
Python, land it in DuckDB alongside the repo dataset (or standalone),
write 10 to 15 analytical SQL queries, build a dashboard in a free tool
(Metabase local via Docker is optional; Tableau Public or a plain Python
matplotlib PNG set is the default so nothing blocks), write a README with
the project-readme-template, publish to GitHub, record a 10-minute
walkthrough video. Step-by-step with checkpoints and a rubric she can grade
herself against. Includes three suggested project ideas with the API named
for each, and guidance on picking one in 15 minutes rather than agonizing.

### 10-the-se-craft
What an SE actually does across a deal: discovery, demo, POC, technical
Q&A, security review, handoff to implementation. Discovery: the question
framework (current state, pain, desired state, technical environment,
decision process), with 20 sample questions. Demo: tell-show-tell, start
with the outcome, the "demo the problem, not the features" rule, handling
"can it do X" live, recovering when something breaks. POC scoping: success
criteria in writing. Objection handling for the five technical objections
every SE hears. Working with the AE. Walkthrough: write a discovery-call
notes doc and a 10-minute demo script for the capstone project using the
templates, then record it. Tie-in throughout: her CS internship already
trained the listening half of this job, name that explicitly.

### 11-job-search-kit
Target titles and what each really means (associate SE, SE academy
programs, solutions consultant, implementation specialist, sales engineer
associate, technical account manager). Where the postings are. How to read
a posting and build a gap list. Résumé: the bullet formula (action, tool,
outcome, number), before-and-after rewrites of CS-intern bullets into
SE-adjacent bullets, a projects section example built from the capstone.
LinkedIn: headline formula, the "about" paragraph, posting the demo video.
Interview prep: 20 technical questions with model answers at the depth an
associate SE needs, 15 behavioral questions with the STAR structure, the
take-home demo assignment and how to approach it, questions to ask them.
A 30/60/90 plan template for the first job. Network: how to ask for an
informational interview in three sentences, with a message template.

### Root files
- `README.md`: one paragraph on who this is for, the module table with one
  line each, the 8-week path, how to start today (three commands), how to
  use `progress.md`, license, and an honest line that this was assembled by
  Isaac with AI assistance for a specific learner and is shared as-is.
- `progress.md`: checkboxes for every module, every exercise set, every
  artifact (learning-log repo, capstone repo, demo video, updated résumé,
  LinkedIn post, first 10 applications).
- `glossary.md`: alphabetized, one line per term, filled by the builders as
  they define terms.
- `templates/*`: short, fill-in-the-blank, with one completed example each.

## Acceptance criteria (whole repo)

- Every module follows the fixed template exactly, including the three
  "You can now say" sentences and the résumé bullet section.
- Every exercise has a solution in `solutions.md`, and every SQL solution
  has been executed against the generated dataset and returns rows.
- `datasets/generate.py` runs with `python generate.py` on Python 3.10+
  with no third-party imports and regenerates identical CSVs (seeded).
- All internal links resolve. All Mermaid blocks render (fence with
  ```` ```mermaid ````).
- No module exceeds about 2,500 words of prose excluding code blocks.
- Glossary contains every term introduced in bold in any module.
- Nothing requires a paid tool. Docker and Metabase are optional paths only.
- No emoji. No exclamation marks in headings.

## Deviations

Recorded by builder B for modules 06-11.

- **Word budget.** The acceptance criterion "no module exceeds about 2,500
  words of prose excluding code blocks" is not reachable for modules 06 and
  08-11 alongside the same document's own module specs, which mandate 20
  discovery questions, five objections with responses, 10 security-
  questionnaire answers, a 14-row self-grading rubric, an eight-step capstone
  walkthrough, and 35 interview questions. Measured on paragraph text only
  (excluding code fences, tables, list items, and the required checkpoint
  answer blocks), modules 06-11 run 1,823 to 2,307 words and are within
  budget. Measured on every non-code word, they run 2,633 to 4,192. The
  budget is interpreted as paragraph prose. No required content was cut.
- **Question banks live in `solutions.md`.** Modules 10 and 11 place the model
  answers to the 20 technical and 15 behavioral interview questions in
  `solutions.md` rather than the README, consistent with the writing rule
  "solutions in a separate file so she tries first."
